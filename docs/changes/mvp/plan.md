# Accountable MVP 實作計畫

依據[產品意圖](intent.md)、[設計規格](../../spec.md)、[技術堆疊](../../TECH_STACK.md)及選定的 [A · 跟進工作台](../../mockups/1-follow-up.html)實作。此版提供單人在自己的電腦離線操作的 CRM，涵蓋儀表板、公司、聯絡人、商機與商機看板。資料由 FastAPI 寫入本機 SQLite，介面使用繁體中文及新臺幣。產品範圍與八項驗收條件以規格為準。

## Order of work

### 1. 建立可啟動的前後端

- 依技術堆疊建立 npm workspace 與 uv 專案。把相依套件安裝與日常啟動分開，備妥套件後以 `uv run --no-sync` 啟動後端。開發指令以跨平台方式啟停兩個服務，預設各綁定本機回送介面。React 一律用相對 `/api` 路徑，開發時由 Vite 代理。選用成熟的表格、圖表與拖放套件，確認可在套件安裝後由本機載入，並以 lockfile 固定相依版本。
- 建立頂端五項導覽與路由。首頁 `/` 是儀表板，列表使用 `/companies`、`/contacts`、`/deals`，詳情使用各列表路徑加上 `/:id`，看板使用 `/pipeline`。確認可以直接開啟及重新整理詳情網址，並使用瀏覽器上一頁、下一頁。
- 為列表、詳情、時間軸、看板與儀表板提供共用的讀取狀態。載入時顯示進度，失敗時以繁體中文說明原因並提供重試入口。重試只重新讀取失敗的資料，成功後顯示該頁結果。
- **完成條件**　`npm run dev` 啟動兩個服務，瀏覽器能開啟首頁、切換導覽並透過代理取得 `/api/health` 回應。停止指令後兩個服務都結束。

### 2. 建立資料表、初始化與範例資料

- 用 SQLAlchemy Core 定義公司、聯絡人、商機及活動。公司與聯絡人可被商機參照，活動必須且只能有一個聯絡人或商機擁有者。啟用 SQLite 外鍵，依規格分別處理清除關聯及刪除附屬活動。商機存整數分、整數機率、預計與實際結案日兩個獨立欄位及欄內順序。跟進與結案日使用本機日曆日期，活動時間統一為 UTC，前端轉成本機時間。
- 日常資料預設儲存在 repo 根目錄下的 `data/accountable.sqlite3`，由既有 Git 規則忽略。應用程式與重設指令都可用 `ACCOUNTABLE_DB_PATH` 指定路徑，供測試與驗收使用。首次建立資料表與填入範例資料時使用明確的初始化記錄，正常重啟時沿用現有資料，即使使用者已清空紀錄。初始化與重設在交易中完成。
- 測試啟動器每次建立專用暫存目錄，將目錄與其中的資料庫絕對路徑明確傳給後端及重設程序。測試模式在開啟 SQLite 前共用路徑檢查。當 `ACCOUNTABLE_DB_PATH` 未設定、解析後落在當次暫存目錄之外，或指向日常資料庫時，以錯誤中止。路徑比對須解析符號連結。pytest 使用同一套檢查規則。
- 範例資料包含多產業、三種聯絡人狀態、六個商機階段、近幾月成交與失單、未來結案與逾期商機，以及不同類型和期限的跟進活動。日期相對於初始化當日。讓 `npm run seed` 重設指定的本機資料庫，並在操作文件說明會清除現有資料。
- **完成條件**　全新資料庫各功能有資料可讀。寫入或清空一類紀錄後重啟，資料維持原狀。在一次性資料庫執行重設，恢復完整範例資料。

### 3. 建立 API 與業務規則

| API 路徑 | 契約 |
| --- | --- |
| `/api/companies`、`/api/contacts`、`/api/deals` 及各自的 `/{id}` | 用 `GET`、`POST` 操作集合。用 `GET`、`PATCH`、`DELETE` 操作單筆。列表包含畫面所需的關聯名稱。公司詳情含關聯聯絡人及商機摘要，聯絡人與商機詳情回傳關聯識別碼和名稱。 |
| 公司、聯絡人與商機的詳情路徑加上 `/delete-impact` | 用 `GET` 回傳確認視窗用的受影響筆數，依紀錄種類區分解除關聯、活動及其中未完成跟進。確認時以 `DELETE` 的查詢參數帶回畫面顯示的各項筆數。若筆數已改變，回傳 `409` 與最新筆數。 |
| `/api/contacts/{id}/activities`、`/api/deals/{id}/activities`、`/api/activities/{id}` | 用 `GET`、`POST` 依擁有者讀取時間軸或新增手動活動，用 `PATCH`、`DELETE` 依活動識別碼編輯、標記跟進完成或刪除。 |
| `GET /api/pipeline`、`POST /api/deals/{id}/move` | 取得依階段與順序排列的卡片及統計。移動時提交目標階段與可省略的插入點卡片識別碼。 |
| `GET /api/dashboard` | 回傳待跟進、最新 10 筆活動、本月成交與進行中摘要、含本月的六個月成交序列及六階段金額。 |

- 由 API 驗證必填欄位、外鍵、列舉、非負整數分、0–100 整數機率及日期。維持統一的欄位與一般錯誤格式，查無識別碼回傳 `404`。表單驗證金額最多兩位小數再轉成整數分送出。讀取及統計也傳遞整數分，由前端轉為新臺幣顯示。
- 刪除公司時清除聯絡人及商機的公司連結。刪除聯絡人時清除商機的主要聯絡人連結，刪除該聯絡人的活動。刪除商機時一併刪除該商機的手動與系統活動。每次刪除與關聯處理在同一交易完成。未完成跟進筆數僅計有跟進日且尚未完成的活動。系統活動的原始內容由後端保護。
- 刪除公司、聯絡人或商機時，先在同一筆寫入交易內按預覽的規則重新計算各項筆數，比對一致才執行刪除。若不同，保留資料並回傳最新影響，待使用者重新確認。
- 以同一套商機階段規則處理表單和跨欄拖放。依欄序套用 10%、25%、50%、75%、100%、0% 的預設成交機率，實際換階段才覆寫手動機率並新增一筆系統活動。跨入成交或失單時以本機今日作為預設實際結案日，成交與失單互換時保留實際結案日，重開時清除實際結案日並沿用原預計結案日。已結案商機可在表單更正實際結案日為今天或過去日期。
- 從列表表單或看板直接新增成交或失單商機時，表單預帶本機今天為實際結案日，API 在未提供該日期時套用同一預設。建立紀錄只儲存初始階段，系統階段活動由後續實際換階段時產生。
- 新增或透過表單換階段時放到目標欄首。拖放以插入點卡片識別碼定位，省略時放到欄末，空欄即唯一位置。驗證插入點屬於目標欄，從原順序移除正在移動的卡片後再插入並重編受影響欄。對同欄拖回原位置視為無變更。同欄移動僅更新順序；跨欄移動在同一交易儲存順序、階段、機率、結案日與系統活動。
- 後端對商機列表和看板回傳同一條件算出的逾期狀態。僅進行中且預計結案日早於本機今天的商機為逾期。待跟進依本機日曆日分為逾期、今天、未來七天內、稍後到期，組內依到期日排序。待跟進資料與最新活動提供可導向時間軸的識別碼。
- 每月成交依目前為成交的商機的實際結案日計算，六個月序列補齊空月。進行中統計只計前四個階段，各範圍先加總金額乘機率，再四捨五入至分。看板已結案欄的進行中合計與預期營收為零，儀表板的六階段金額涵蓋成交與失單。
- **完成條件**　pytest 驗證 CRUD、刪除關聯、活動、階段轉換、拖放排序與統計。交易中途失敗時，既有紀錄、排序與活動維持原狀。

### 4. 完成公司、聯絡人與商機的列表及表單

- 以共用表格元件提供搜尋、欄位升降冪、新增與每列詳情、編輯、刪除入口。搜尋去除前後空白，英文字母不分大小寫，按規格各自比對指定欄位。聯絡人的狀態篩選可和搜尋同時使用。金額、機率與日期依原始值排序。以不同訊息顯示空資料及無搜尋結果。
- 表單顯示必填與欄位錯誤，儲存失敗時保留輸入。刪除先讀取影響筆數並顯示具體結果。使用者取消時關閉視窗。後端回傳 `409` 時，以最新筆數更新確認視窗，等候使用者再次確認。刪除成功後更新列表及受影響資料，失敗時保留原列。商機表單依階段呈現對應的結案日期，儲存後列表顯示後端回傳的日期、機率與逾期狀態。
- **完成條件**　三類資料可各自新增、查找、排序、編輯與刪除。列表取用已儲存的值，重新整理後維持變更。

### 5. 完成詳情頁及時間軸

- 公司詳情呈現關聯聯絡人與商機，聯絡人及商機詳情呈現既有的關聯連結。詳情網址指向已刪除紀錄時，提供繁體中文說明與返回列表入口。
- 聯絡人與商機依時間由新到舊呈現活動。可新增、編輯、刪除備註、通話及電子郵件，設定或移除跟進日期，也可標記完成。系統階段活動以唯讀紀錄顯示。重用表單錯誤處理及刪除確認行為。
- **完成條件**　從列表及關聯連結可到達正確詳情，手動活動變更會更新時間軸，商機在表單實際換階段時出現一筆系統活動。

### 6. 完成商機看板

- 依 A 稿配置上方統計橫列、六個階段欄、欄首統計及新增入口。欄首新增沿用商機表單，預帶該欄階段與機率。卡片顯示名稱、公司、金額、機率、結案日及逾期標示，並可開啟商機詳情。較窄筆電在看板區內水平捲動。
- 同欄與跨欄都提供欄首、卡片間、欄末和空欄落點。用拖放後的下一張卡片當插入點，把卡片位置轉成 API 參數。同一筆移動等待伺服器回應時避免重複送出。成功後以已儲存結果更新卡片、欄統計和整體統計，並讓列表、詳情及儀表板讀取最新資料。
- 確定未儲存時，恢復拖放前的畫面並顯示錯誤。遇到逾時或連線中斷時，提示結果待確認，重新讀取看板，並讓列表、詳情和儀表板重新取資料。顯示伺服器最後查到的狀態，避免自動重送移動。若仍無法讀取，保留待確認訊息和重試讀取入口。
- **完成條件**　跨欄結果可在看板、列表與時間軸互相核對。同欄及跨欄位置在重新整理和重啟後一致，空欄可接收卡片。

### 7. 完成儀表板

- 依 A 稿先呈現左側待跟進與右側近期活動，再呈現成交與進行中摘要、成交金額折線圖、成交筆數長條圖與六階段金額。金額用 `NT$` 及千分位，圖表月份、指標與階段皆使用繁體中文標籤。
- 待跟進與近期活動連到對應時間軸；使用者可直接標記跟進完成。每次變更活動、跟進或商機後，重新取得受影響的查詢結果。讀取失敗顯示可重試的訊息，統計載入時顯示載入狀態。
- **完成條件**　從首頁進入時間軸新增跟進，返回後可查到該項，標記完成後移出待辦且活動仍在。當月成交、進行中統計與圖表數值可用已知資料核對。

### 8. 整合測試與本機操作文件

- 根目錄 `npm test` 依序執行 Vitest、pytest 與 Playwright，任一階段失敗即回報非零狀態。Playwright 使用已安裝的 Chrome，只連到該次測試啟動的前後端。測試使用專用連接埠，若已被使用就回報錯誤，避免沿用現有服務。測試使用各自的暫存 SQLite 或在當次專用暫存目錄重設資料，重設與重啟均沿用同一個測試路徑。
- 以本機資源提供字型與圖表，依兩張 A 稿截圖檢查桌機及較窄筆電的版面。在 `docs/STATUS.md` 記錄工具、套件安裝、啟動網址、資料庫位置、測試指令及重設會清除本機資料的效果。
- **完成條件**　無須事先啟動服務即可通過 `npm test`。相依套件備妥後，在 Mac 斷網啟動並依下方手動驗收操作五個區塊。

## Risks

| 風險 | 處理與確認 |
| --- | --- |
| **最高風險是測試或重設誤用日常資料庫。** 一次測試重設就可能清除日常資料。 | 後端與重設程序在測試模式先驗證專用暫存路徑，Playwright 只使用本次啟動的服務。測試路徑缺失、誤指日常資料庫或連接埠已被使用時，確認程序中止且資料仍在。 |
| 跨欄拖放只儲存部分資料，或已儲存但瀏覽器未收到回應。 | 卡片順序、階段欄位與系統活動共用交易。分別驗證寫入回滾、請求遭拒，以及已寫入後回應遺失時重新取得正確資料。 |
| 刪除關聯方向錯誤，或預覽後有人新增關聯。 | 預覽與刪除採同一組查詢條件。寫入交易內重算筆數，若與確認內容不同就回傳新的影響供再次確認。 |
| 午夜、月底與金額小數造成逾期分組或報表偏差。 | 後端用同一個可固定的本機日期來源，測試今日、第七天、第八天及跨年月份。以整數分儲存、加權後按統計範圍四捨五入，測試數筆金額加總才能判定的邊界。 |
| 儲存後頁面仍顯示舊資料，或外部資源令離線畫面不完整。 | 成功後重新查詢受影響資料，失敗保留輸入與現有資料。以真實 Chrome 檢查頁面更新及斷網啟動，字型、樣式與圖表資源均由本機提供。 |

## Proof

以下編號對應[設計規格的驗收條件](../../spec.md#驗收條件)。每階段先執行相關測試，整合後以 `npm test` 執行全部自動測試。

### 單元與 API 測試

| 工具與測試案例 | 驗證結果 | 對應 |
| --- | --- | --- |
| pytest · 建立新庫、寫入後重啟、清空列表後重啟、重設 | 資料只在初始化和明確重設時填入。正常重啟保留修改與空列表。重設恢復各階段、狀態及活動範例。 | 1、2 |
| pytest · 驗證測試路徑 | 在隔離的測試環境放置一份代表日常資料的資料庫。讓啟動與重設程序分別遇到路徑缺失、路徑指向該庫，以及符號連結繞到暫存目錄外的情況。兩個程序都應中止，並核對該庫中的原有紀錄仍在。當次專用路徑則可正常啟動及重設。 | 1、2 |
| pytest · 欄位驗證、讀寫、關聯及刪除影響 | 無效金額、機率、日期、擁有者或外鍵會回報欄位錯誤。比對公司、聯絡人和商機的影響筆數與刪除後結果。強制交易失敗後，原紀錄與關聯仍存在。 | 2、3 |
| pytest · 刪除預覽後關聯變更 | 預覽商機的刪除影響後，從另一個請求新增一筆未完成跟進。以舊筆數送出刪除應回傳 `409`，活動總數與未完成跟進筆數各加一，商機和活動仍在。以最新筆數確認後，按規格刪除兩者。 | 2 |
| pytest · 直接新增已結案商機 | 固定本機日期，分別新增成交和失單商機，省略實際結案日。兩筆都應儲存本機當天的實際結案日，時間軸維持空白。 | 4、5 |
| pytest · 修改商機、移動卡片及交易失敗 | 一般編輯及同欄拖放保留機率。既有商機實際換階段套用預設機率並寫一筆活動。驗證成交、失單互換、重開，以及昨日、今日和未填結案日對逾期的影響。驗證欄首、中間、欄末、空欄、無效插入點及重啟後排序。強制活動寫入失敗後所有變更回復。 | 4、5 |
| pytest · 活動、跟進及近期活動 | 兩類時間軸皆由新到舊呈現，手動活動可編輯刪除，系統活動保留。以固定日期驗證逾期、今天、第七天、第八天，完成或移除跟進日後移出待辦，近期活動最多十筆。 | 5、6 |
| pytest · 儀表板與看板統計 | 以已知金額驗證預期營收，涵蓋加總後才四捨五入。驗證六個日曆月含空月、成交與重開後數值變化、六階段原始金額，以及看板已結案欄的進行中金額為零。 | 4、6、7 |
| Vitest · 表格、表單及格式 | 搜尋忽略空白與英文字母大小寫，可疊加聯絡人狀態篩選。金額依數值排序，顯示 `NT$` 與千分位。欄位驗證及儲存失敗保留表單值。 | 2、3、7 |
| Vitest · 看板落點及逾期顯示 | 前端為欄首、中間、欄末與空欄產生正確的插入點。依 API 的逾期狀態，在列表與卡片呈現一致的文字標示。 | 4 |

### Mac 與 Chrome 手動驗收

1. 完成相依套件安裝後斷網，執行 `npm run dev`。在 Chrome 由首頁走訪五個區塊，核對範例資料及操作。使用專供驗收的資料庫新增或編輯一筆後停止並重啟，再執行 `npm run seed`，確認重啟保留變更、重設恢復範例資料。對應驗收 1、2。
2. 在桌機與較窄筆電視窗，將儀表板與看板和 A 稿的[儀表板截圖](../../mockups/1-follow-up-dashboard.png)、[商機看板截圖](../../mockups/1-follow-up-pipeline.png)對照。核對區塊順序、品牌色、繁體中文、`NT$`、圖表指標、逾期標示及看板內水平捲動。對應驗收 7。
3. 在 `npm test` 通過後，以實際業務流程操作五個區塊。從待跟進進入詳情並記錄下一步，操作三類列表的新增、搜尋、排序、編輯、取消及確認刪除與關聯導覽，再調整看板順序、跨欄至成交並核對儀表板。逐頁檢查畫面及瀏覽器主控台，記錄結果。對應驗收 2–8。
