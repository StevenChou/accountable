這一天在做什麼

Day 3 的課名是「Anthropic AI-SDLC」。你要從 docs/intent.md 這份商業層級的描述出發，做出 Accountable 的 MVP：一個給一個人、在自己電腦上用的業務 CRM。過程照 Anthropic 的 AI-native SDLC 分成六個階段：Plan、Design、Build、Test、Deploy、Maintain，全部在一個叫 mvp 的分支上進行，每個階段結束時由你 commit 一次。

開始前先 fork 這個 repo，因為今天最後要用 pull request 把你寫的文件分享出去。

做完之後，docs/ 會多出 spec.md、mockups/、plan.md、REVIEW.md，intent.md、STATUS.md、AGENTS.md 會修改。程式碼依 docs/TECH_STACK.md 放在 frontend/（React、Vite）、backend/（FastAPI、SQLite）、e2e/（Playwright Test），根目錄會有 package.json、pyproject.toml、uv.lock。

名詞解釋

SDLC
Software Development Life Cycle，軟體從規劃到維護的流程。今天用 Anthropic 版本的六個階段：Plan、Design、Build、Test、Deploy、Maintain。
MVP
Minimum Viable Product，第一個可以實際使用的版本。範圍和「不做什麼」寫在 docs/intent.md。
intent（docs/intent.md）
要解決的問題、預期成果、限制、成功標準。說「要什麼、為什麼」，不說怎麼做。
spec（docs/spec.md）
把 intent 轉成需求和設計。第 4 步由 agent 寫，你回答它列出的疑慮。
mockup（設計稿）
不接資料的靜態 HTML 畫面，只用來看外觀和版面。第 5 步做三份，你選一份。
plan（docs/plan.md）
怎麼做：會變動的檔案、分階段的工作順序、風險、用哪些測試證明完成。
fork
在你的 GitHub 帳號下複製一份別人的 repo。你不能直接推到 Ed 的 repo，所以先推到自己的 fork，再從 fork 發 PR。
remote：origin 與 fork
本機 repo 記錄的遠端位址名稱。origin 是你 clone 的來源，也就是 Ed 的 repo；fork 是第 1 步加的、你自己的那份。
branch（分支）
從某個 commit 分出去的一條工作線。在 mvp 上做 MVP，main 不動，到第 13 步才合回去。
merge
把一個分支的 commit 合進另一個分支。第 13 步把 mvp 合進 main。
pull request（PR）
請 repo 的擁有者把你分支上的變更合進他的 repo。第 15 步從你的 fork 發給 ed-donner/accountable。
unit test 與 end-to-end test
unit test 單獨測一個函式或元件；end-to-end test 啟動整個 app，在瀏覽器裡像使用者一樣操作。
Playwright MCP 與 Playwright Test 補充
今天兩個都會用到。Playwright MCP 是 Day 2 第 7 步加的，讓 Claude 操作瀏覽器、截圖（第 5、9 步）。Playwright Test（@playwright/test）是寫 end-to-end test 的框架，docs/TECH_STACK.md 指定用它。
npm test
一個指令跑完所有 unit test 和 end-to-end test，有任何一個失敗就回報失敗。第 8 步建立。
review policy（審查政策）
docs/REVIEW.md：審查時要看哪些面向、什麼算必須修正。第 11 步由你自己寫。
Important 與 nit
審查的兩種發現。Important 必須在 merge 前修正；nit 是風格、命名這類小問題，不擋 merge，每次最多回報五個。
fresh session（新 session）
清空 context、重新開始的對話。Claude Code 用 /clear。新 session 不記得前面的對話，只能讀 repo 裡的檔案。
usage limit（用量上限）
訂閱方案有 5 小時和每週兩種上限。到了上限 agent 會停下來，說明何時重置。見用量上限與 session。

課程英文範本 · docs/REVIEW.md
# Review policy

Every change is reviewed against this policy before it merges. The reviewer reports its findings and doesn't change any code.

## Passes

Make a separate pass over every change for each of these:

- **Bugs:** the code does what it's meant to, including when something goes wrong.
- **Security:** no secrets or personal data are exposed, and nobody can do what they shouldn't.
- **Matches spec.md and plan.md:** the change does what those documents say, with nothing missing and nothing extra.

## Important

An Important finding must be fixed before the change merges. A finding is Important if the change breaks behavior that should work, leaks data or breaks a rule in AGENTS.md.

## Nits

A nit is a small point, such as style or naming, that doesn't block the merge. Report at most five per review.
中文意思
開頭Review policy每個變更在 merge 前都依這份政策審查。審查者只回報發現，不改任何程式碼。
BugsPasses程式做到它該做的事，包括出錯的時候。
SecurityPasses沒有洩漏 secret 或個人資料，也沒有人能做不該做的事。
符合 spec 和 planPasses變更做到 spec.md 和 plan.md 說的，沒有缺漏，也沒有多做。
ImportantImportantmerge 前必須修正。符合任一項就算：弄壞了應該正常運作的行為、洩漏資料、違反 AGENTS.md 的規則。
NitsNits風格、命名這類小問題，不擋 merge。每次審查最多回報五個。

三個 pass 的意思是：每個面向各看一遍，不是一次看完全部。

白話說明

第 12 步的審查會照這份檔案進行。什麼算「必須修」、什麼可以先放著，是專案擁有者的判斷，所以講義要你自己建立這個檔案，而不是請 agent 寫。

nit 限五個，是避免審查結果被大量小問題淹沒，讓 Important 的項目容易看到。

agent 自己 commit 時

內容來自 course/for_agents/AGENT_GIT_GUIDE.md 的 If the agent has committed 課程指南。課程把 commit 留給你，但 agent 有時還是會邊做邊 commit，例如每個 phase 做完時。這不會遺失任何東西。

  1. git commit 顯示「nothing to commit, working tree clean」，表示 agent 已經全部 commit 了。git log --oneline 會列出它的 commit，最新的在上。
  2. git branch 用 * 標出目前的分支。確認是 mvp，不是 main。
  3. 保留這些 commit 繼續做。如果 git status 還有變更，用該階段的訊息 commit。

想要每個階段只有一個 commit

merge 前把 agent 的 commit 合成一個。在 git log --oneline 找到這個階段開始前的最後一個 commit，用它的 hash：

終端機
git reset --soft <hash>
git add .
git commit -m "Build: the MVP"

--soft 保留所有變更，只替換 commit。只能用在還沒 push 的 commit 上。

commit 落在 main 上（忘了先開分支）

在 git status 乾淨的狀態下，<hash> 是這個階段開始前的最後一個 commit：

終端機
git branch mvp
git reset --hard <hash>
git checkout mvp

git branch mvp 讓 agent 的 commit 留在 mvp 上，git reset --hard 把 main 移回這個階段開始前的位置。
