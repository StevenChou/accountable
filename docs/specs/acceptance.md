# 驗收條件

下表列出目前產品的驗收方式。手動驗收使用 Mac 上的 Google Chrome，開發與測試指令的相容目標涵蓋 macOS、Linux 與 Windows。

| 編號 | 驗收方式 |
| --- | --- |
| 1 | 預先安裝相依套件後，在 Mac 斷網執行 `npm run dev`，從 Chrome 以虛構使用者登入並開啟儀表板，確認五個區塊皆有範例資料且可操作。 |
| 2 | 在公司、聯絡人和商機各新增一筆，依關鍵字查找、切換欄位排序、編輯並刪除。刪除前取消一次，再驗證確認視窗所列的筆數與實際關聯變更。確認期間若關聯筆數變動，須以新筆數重新確認。重新整理及重啟確認變更保留，使用驗收用資料庫執行 `npm run seed` 並確認範例資料恢復。 |
| 3 | 逐一切換聯絡人的三種狀態篩選。開啟公司查看旗下聯絡人與商機，再從聯絡人和商機詳情開啟已存在的關聯。 |
| 4 | 將手動調整過機率的商機拖到另一欄，確認階段和預設機率出現在列表，並確認看板與各欄統計立即更新。在同一欄及跨欄拖到首、中、末位置，含放入空欄，重新整理後比對順序。從指定欄新增商機，並在列表和卡片上看到逾期標示。分別驗證移動遭拒及已儲存後回應遺失，確認看板會顯示正確位置。 |
| 5 | 在聯絡人和商機的時間軸新增、編輯及刪除手動活動，確認由新到舊排序。以表單和拖放變更階段，每次各出現一筆系統活動。檢查待辦日期分組，包含今天、第七天和第八天的邊界。標記完成後從待辦移除，時間軸仍保有活動。 |
| 6 | 從儀表板點入一次聯絡人或商機時間軸並新增跟進，回到首頁查看結果。使用已知金額與機率核對預期營收，再將商機標為成交，確認當月成交筆數、金額與進行中合計反映變更。 |
| 7 | 逐頁目視檢查淺色介面、繁體中文、品牌色及 `NT$` 金額。從圖表名稱和數值確認折線圖、長條圖與六階段視覺化的指標，並在筆電寬度檢查可操作性。 |
| 8 | `npm test` 通過後，在 Mac 上以 Chrome 用虛構使用者登入，從儀表板走訪五個區塊，依日常業務流程實際做一遍上述操作，逐頁檢查畫面，確認瀏覽器主控台無錯誤。 |
| 9 | 以端對端測試確認首次開啟預設亮色、從使用者選單切換後即時套用、跨頁與重新整理後保留主題，以及「找不到頁面」也能切換。關閉瀏覽器後再用同一瀏覽器開啟 Accountable，確認仍採用上次的選擇。清除網站資料後確認回到亮色。 |
| 10 | 用鍵盤操作登入表單、全站搜尋、使用者選單及主題設定，確認焦點和目前選擇可辨識。在兩種配色下檢查登入畫面、圖表標籤與提示、商機階段與逾期標記、表單、對話框及訊息，量測文字與背景對比。亮色的各 CRM 頁面沿用原本的配色及版面，頂欄呈現搜尋及使用者選單。儀表板和商機看板在亮色與深色各保存一張截圖，共四張。 |
| 11 | 分別在有及無正式 Supabase 設定的環境執行 `npm run check`。每次都須通過，使用獨立的 SQLite 與虛構使用者。確認整個檢查過程沒有連線至 Supabase，正式資料也沒有變動。以相同的本機資料執行 `ui-check`。 |
| 12 | 未登入時開啟首頁、各列表、紀錄詳情、看板及不存在的路徑，確認均顯示登入畫面。直接呼叫受保護的讀取、寫入及搜尋 API，確認缺少、無效或逾期權杖均收到 HTTP 401。以有效帳號從紀錄網址登入，確認開啟該紀錄、重新整理仍可使用，再走訪其他區塊操作。從選單登出，確認回到登入畫面且返回或重整都無法進入 CRM。 |
| 13 | 成員 A 新增公司、聯絡人、商機及活動，逐一確認詳情及時間軸顯示 A 的完整 Email。成員 B 登入後可查看並編輯同一批資料，確認新增者仍是 A，資料記錄 B 為最後修改者。由 B 變更商機階段，確認新產生的系統活動標示 B 的 Email。 |
| 14 | 從頂欄輸入公司、聯絡人及商機的名稱或姓名片段，再換用不同大小寫和前後空白查詢。從各類型結果開啟對應詳情，並核對空白輸入、無結果及查詢失敗時的狀態。在正式模式驗收時，以相同資料及查詢核對 Postgres 與本機 SQLite 的符合紀錄。 |
| 15 | 從使用者選單分別選擇亮色、深色及跟隨系統。在系統模式下切換裝置設定，確認頁面即時跟隨，重新開啟及登出後仍套用所選模式。固定亮色或深色時，裝置設定變動不改變所選配色。 |
| 16 | 用與 Render 相同的正式啟動流程在本機執行建置後的應用程式，確認 migrations 完成，能用管理者建立的 Supabase 帳號登入並讀取共用資料。以瀏覽器公開設定及成員權杖直接查詢 Supabase 公開資料 API，確認 CRM 資料受 RLS 限制。部署後從 Render 網址驗證相同的登入及讀取流程。 |

從 repo 根目錄執行 `npm run check` 驗收。完整檢查包含 `npm test`，依序執行 Vitest 前端單元測試、pytest 後端單元測試與 Playwright Test 的 Chrome 端對端測試，任一測試失敗時命令須回報失敗。測試自行啟動必要的服務，並使用獨立的 SQLite 資料庫和虛構使用者。

[GitHub Actions](../../.github/workflows/ci.yml) 在每個分支推送後先掃描 Git 歷史，再執行 `npm run check:quick`，檢查格式、lint、型別、機密及含覆蓋率的單元測試。待合併提交的 Playwright 驗收由本機完整檢查執行。
