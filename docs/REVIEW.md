# 審查政策

所有變更都要在合併前依本政策審查。審查者在審查階段只回報發現。

## 審查面向

以下三個面向各自審查一遍，每一遍都涵蓋所有變更。

- **功能與錯誤處理**。確認程式行為符合預期，並妥善處理失敗情況。
- **安全性**。確認機密資訊與個人資料受到保護，且操作權限符合預期。
- **符合規格、實作計畫與撰寫標準**。先從索引找到本次變更涉及的區域規格、適用的共用規則及驗收條件，再對照程式、測試和當前分支的 `docs/changes/<branch name>/plan.md`（若有），確認行為和範圍符合要求。[規格索引](spec.md)
- 審查規格時，確認受影響的文件已同步更新。指出本次變更新增或修改、但區域規格或共用規則未描述的程式行為，並附上程式位置。
- 對照程式撰寫標準審查變更，回報不符合的規則與程式位置。[程式撰寫標準](STANDARDS.md)

## 登入與部署的驗證

- 登入、還原工作階段及刷新權杖都要驗證認證服務暫時不可用的情境。有效的工作階段應保留供重試，明確的未授權回應才清除登入。
- 核對部署的團隊時區、資料庫所在區域、分支、執行環境與環境變數名稱。日期相關功能以團隊時區驗收，新增的 migration 應納入格式、lint 及型別檢查。

## 必須修正的問題（Important）

變更若破壞應正常運作的行為、造成資料外洩，或違反 `AGENTS.md` 的規則，須列為 Important，並在合併前修正。[專案規則](../AGENTS.md)

## 小問題（Nits）

風格或命名等小問題可在合併後處理。每次審查最多回報五項。
