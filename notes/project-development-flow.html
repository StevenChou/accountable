Accountable 課程筆記 · Week 1 Days 2–4

專案開發流程速查

從設定 coding agent 到合併後試用。選擇你的起點，用流程圖確認每一步要做什麼、交出什麼證據。

選擇專案起點 跳到開發流程圖

開工前確認環境

  • 環境與共用規則

    裝好 Git、coding agent 和專案工具。在 repo 根目錄確認 agent 能讀到 AGENTS.md 的共用指示，個人偏好留在使用者設定。Day 2 安裝與設定

  • 權限

    允許 agent 執行明確的測試指令。git push 由人確認，限制 agent 讀取 .env。Day 2 權限設定

  • 介面工具

    有介面工作時，用品牌 skill 統一設計。讓 agent 用 Playwright MCP 操作瀏覽器、比對畫面及截圖。

從哪裡開始

做第一個 MVP

課程從自己的 fork 開始。用 docs/intent.md 和 docs/plan.md 記錄首版，並建立 docs/spec.md。Day 3 的 MVP 起點

開分支做 MVP

修改既有專案

先讀產品規格 docs/spec.md。把這次的 intent.md 和 plan.md 放進 docs/changes/<分支名>/，並確認下方的 harness 設定齊全。Day 4 的變更起點

開分支做變更

展開 Harness 設定清單

  • 文件與審查規則

    從 AGENTS.md 指向產品規格、當前變更、STANDARDS.md、REVIEW.md 和 IMPROVE.md。

  • 本機檢查

    開發中跑快速版，驗收時跑含端對端測試的完整版。Git hook 在提交前處理格式、lint、型別與秘密掃描。

  • CI 與秘密保護

    每次推送先掃秘密，再跑完整檢查。將金鑰留在 Git 已忽略的 .env。agent 支援時，加入阻擋編輯該檔案的 hook。

Accountable 用 npm run check:quick 與 npm run check。套用到其他專案時，換成該專案的指令。Day 4 的 Harness 設定步驟

每次變更照流程走

  1. START

    開變更分支

    確認工作區與起始版本，從自己的主分支開一條分支。

  2. Plan

    先寫清楚要解決什麼

    請 agent 訪談你，把答案寫入 intent.md。Day 3 訪談範例

    完成判準 問題、使用者、範圍和可驗證的成功標準已確認。

  3. Design

    審閱變更後的產品行為

    建立或更新 spec.md，親自讀過差異。有介面改動時先選定設計稿。

    完成判準 已確認變更後的產品行為及本次要採用的設計。

  4. Build

    先排計畫，再分段實作

    在 plan.md 列出改動、順序、風險與測試。開新 session，依計畫分段做、分段測。學員審閱差異與結果後再提交。

    完成判準 計畫中的改動和測試已完成，開發中的檢查通過。

  5. Test

    跑完整檢查，親手驗收

    首次 MVP 用 npm test 跑單元和端對端測試。已設定 harness 就跑完整檢查，例如 npm run check。

    親手走過 intent.md 的成功標準。有介面改動時，用瀏覽器比對設計稿並留下畫面證據。Day 3 瀏覽器驗收

    完成判準 完整檢查通過，成功標準都有驗收證據。

    檢查或驗收未通過

    記下失敗的操作或輸出，修正後重跑完整檢查並重新驗收。

    回 Build 修正
    通過
    1. Deploy

      開新 session 獨立審查

      依 REVIEW.md 審查分支相對主分支的差異。

      完成判準 已完成審查，發現的 Important 問題都已修正並驗證。

      首次 MVP 尚未設定 CI 時，本機驗收和審查都通過後，前往合併判斷。

      有 Important 問題

      依發現修正，重跑受影響的測試與完整檢查，再核對該問題是否已解決。

      回審查確認
      已驗證 · 有 Harness

    2. 改善 harness

      依 IMPROVE.md 回顧審查、人指出的問題與檢查結果。同一錯誤出現兩次時，能自動檢查就加到工具，其餘補到指示或審查規則。

    3. 推送分支並確認 CI

      完成判準 最後一次推送的提交已通過 CI。

      CI 未通過

      看失敗紀錄找根因。修正後跑完整檢查並重推，查看新的執行結果。

      回 CI 確認
      通過

    4. 核對證據，由你決定合併

      核對本機驗收與審查結果。已有 CI 時，確認通過的是這次要合併的提交，再合回主分支。

  7. Maintain

    在合併後的版本試用

    走一遍日常操作，把發現記到 docs/STATUS.md 的 Ideas for later。

    完成判準 記下具體情境，下一次規劃時有據可查。

    回 Plan 開始下一次規劃
