# 深色模式實作計畫

依已確認的變更意圖與產品規格，使用現有的 React、CSS、Recharts、Vitest 和 Playwright 完成。主題偏好保存在目前瀏覽器，沿用現有 API、SQLite 資料格式與套件版本。[變更意圖](intent.md) · [產品規格](../../spec.md#亮色與深色模式)

## Files that change

| 檔案 | 變更 |
| --- | --- |
| `frontend/src/theme.ts`（新增）、`frontend/src/main.tsx`、`frontend/src/App.tsx` | 集中管理主題值與瀏覽器偏好，在 React 掛載前套用已儲存的主題，在共用頁首提供鍵盤可操作的切換控制。 |
| `frontend/src/styles.css` | 定義亮色與深色共用的色彩變數，套用到導覽、面板、卡片、表單、對話框、提示、警示、圖表及商機階段。 |
| `frontend/src/pages/Dashboard.tsx`、`frontend/src/pages/Pipeline.tsx`、`frontend/src/domain.ts` | 圖表和看板引用相同的階段色彩變數。將顏色移出商機階段的資料定義，保留名稱、順序和預設成交機率。 |
| `frontend/src/theme.test.ts`（新增）、`frontend/test/app.test.tsx`、`e2e/dark-mode.spec.ts`（新增） | 補上偏好讀寫、共用控制、跨頁行為與瀏覽器實際配色的測試。 |
| `docs/changes/dark-mode/`、`docs/STATUS.md` | 在 Test 階段保存四張截圖，記錄驗收結果。 |

## Order of work

1. **建立亮色基準與主題切換。** 先用現有 App、同一組範例資料和固定視窗尺寸，記錄儀表板與看板的亮色基準。以單一 `localStorage` 鍵保存 `light` 或 `dark`，掛載 React 前將有效值套用至 `html`，由 `App` 的狀態與共用頁首的按鈕負責後續切換。按鈕顯示目前模式，並讓鍵盤與輔助技術能操作及辨識狀態。首次開啟、讀取失敗或值無效時使用亮色，寫入失敗時本次頁面仍可切換。切換保留現有路由與內容。完成後執行 `npm run test:frontend`。
2. **套用一般介面與共用元件。** 把現有亮色值移到共用色彩變數，讓亮色外觀可對照基準。依品牌規範加入深色頁面背景、黑色面板與 Sea Mist 文字，從文件根元素同步設定 `color-scheme`，讓原生欄位與捲軸適用目前主題。檢查導覽、表格、活動時間軸、空白及錯誤狀態、表單、對話框與遮罩、焦點和停留狀態。用真實 Chrome 核對深色文字及兩種模式下切換控制的對比。
3. **套用儀表板圖表與商機看板。** 讓 Recharts 的座標文字、網格、線條、資料點、長條、數值及提示框使用共用變數。讓儀表板階段標記和看板欄首共用六種階段色，並檢查深色下的成交標記、逾期標示、可放置位置及拖曳中的卡片。保留圖表資料、金額格式及看板操作。完成瀏覽器測試後執行 `npm run test:e2e -- e2e/dark-mode.spec.ts`，再執行 `npm run check`。
4. **完成 Test 階段的驗收證據。** 以現有 Playwright 的 Chrome 與暫存 SQLite 執行完整檢查。依 Proof 手動驗收，並用固定資料與視窗尺寸擷取四張截圖，核對內容後記錄結果。

## Risks

| 風險 | 驗證與處理 |
| --- | --- |
| 深色偏好在重載時太晚套用，或瀏覽器限制儲存 | 在 React 掛載前讀取及套用主題。驗證冷啟動、無效值、清除網站資料，以及讀寫失敗時頁面照常可操作。 |
| 色彩變數整理時改動了亮色外觀 | 保留各項現有亮色值。用相同視窗、樣本與日期比對基準，涵蓋圖表、商機看板及共用元件。 |
| HTML 與 SVG 的預設樣式留下亮色 | 在 Chrome 檢查原生對話框、遮罩、表單控制和 Recharts 的 SVG 與提示框實際渲染結果。 |
| 深色上的資訊、警示、成交標記或次要文字難以辨認 | 沿用階段名稱與「逾期」文字，用同色系色階提升可讀性。量測一般文字至少 4.5:1、大字至少 3:1，並核對成交標記能與深色背景區分。 |
| 頁首加上按鈕後擠壓既有導覽或鍵盤焦點難辨識 | 用桌機與 1024 px 視窗檢查導覽、Tab 順序、焦點與看板內的橫向捲動。 |

## Proof

**單元測試與前端元件測試**

- `frontend/src/theme.test.ts` 驗證無偏好、非法值或讀取失敗時使用亮色，已儲存的 `light` 和 `dark` 皆可讀回。驗證寫入成功及儲存遭拒時，主題仍能套用至目前文件。
- `frontend/test/app.test.tsx` 驗證共用控制顯示目前模式，且可用鍵盤切換並更新狀態。切到深色後開啟列表或詳情，再到「找不到頁面」，仍看到同一控制與目前主題，並可切回亮色。測試之間清理主題屬性和偏好。

**端對端測試**

- `e2e/dark-mode.spec.ts` 在新的 Chrome 瀏覽器環境模擬裝置偏好深色，確認 App 首次仍是亮色。以滑鼠切換深色、確認畫面立即變更，走訪五個功能區塊並重新整理，驗證主題維持。由「找不到頁面」用鍵盤切回亮色後重新整理，驗證亮色也會保存。
- 在 Chrome 檢查至少一個圖表文字或圖形及其提示框、一個商機階段標記，以及共用對話框和錯誤訊息。用實際算出的文字、背景或圖形顏色驗證兩種模式確實套用，並確認標籤、金額與錯誤文字可讀。用暫存資料庫和受控的失敗回應觸發錯誤情境。
- 從 repo 根目錄執行 `npm run check`，涵蓋上述測試與既有格式、lint、型別、機密掃描、覆蓋率及端對端檢查。

**手動驗收與截圖**

- 用獨立的 Chrome 測試使用者設定檔關閉並重開瀏覽器，驗證所選模式仍在。清除該站資料後確認回到亮色。逐頁走訪列表和詳情，查看圖表標籤與提示、對話框、訊息、焦點及商機看板。量測代表性的文字與背景配色，並在 1024 px 驗證導覽和看板可操作。
- 使用同一組範例資料、日期與 1440 × 1000 視窗，由 Playwright 等內容及字型載入後擷取兩頁兩種模式。將 `dashboard-light.png`、`dashboard-dark.png`、`pipeline-light.png`、`pipeline-dark.png` 存在 `docs/changes/dark-mode/`。比對亮色基準時，確認切換控制之外的介面與原有外觀一致。
