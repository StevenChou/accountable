# 變更意圖：登入、搜尋與使用者選單

## 問題

Accountable 目前在單一電腦供一人使用。小型業務團隊需要共用同一份客戶及商機資料，並知道每筆紀錄由誰新增。目前要分別前往公司、聯絡人或商機的列表搜尋，查找跨類型的紀錄要切換頁面。

## 預期成果

- 小型業務團隊使用同一個線上 Accountable。成員登入後可以共用及操作同一份公司、聯絡人、商機與活動資料，並查看每筆紀錄的新增者。
- 成員能從共用頂欄輸入名稱的片段，查找公司、聯絡人和商機，並從結果開啟紀錄詳情。
- 頂欄的使用者縮寫可開啟選單，提供亮色、深色、跟隨系統及登出。首次使用沿用亮色，選擇其他模式後由同一瀏覽器記住。

## 限制

- 正式模式使用 Supabase Postgres，後端繼續透過 SQLAlchemy Core 存取資料。新資料庫使用既有範例資料初始化。測試與本機開發模式用 SQLite、範例資料及虛構使用者，測試使用各自獨立的資料庫。
- Supabase Auth 提供電子郵件與密碼登入。瀏覽器的公開設定只提供 Supabase Project URL 和 publishable key。FastAPI 驗證每次受保護的 API 請求，從驗證後的權杖取得身分，並據此記錄操作人。
- 由管理者在 Supabase 控制台建立使用者，關閉自行註冊。每位已授權的成員可以操作同一份 CRM 資料。透過 Supabase 公開資料 API 的存取由資料列層級安全性（RLS）限制。
- 公司、聯絡人、商機與活動都記錄新增者及最後修改者。介面在相關紀錄或活動上顯示新增者，以帳號的完整 Email 識別。
- 搜尋以名稱或姓名的部分文字比對，忽略大小寫。SQLite 與 Postgres 的比對行為一致。
- 原有的主題切換移到使用者選單。選擇「跟隨系統」時，畫面跟隨裝置的亮色或深色設定。沿用現有的繁體中文介面與鍵盤操作要求。
- 正式模式需要網路連接 Supabase。開發模式、端對端測試及 `ui-check` 使用虛構使用者與本機資料，即使 repo 已設定真實憑證也可離線執行。CI 不需要 Supabase 憑證。既有及新增的單元測試各案例在本機一秒內完成。
- 本機正式模式在 Git 忽略的 `.env` 設定 `DATABASE_URL`、`SUPABASE_URL` 與 `SUPABASE_PUBLISHABLE_KEY`。Render 以免費方案部署單一 Web Service，由 FastAPI 提供建置後的前端及 API，啟動時執行 migrations，並從 Render 的 `onrender.com` 網址提供服務。`render.yaml` 宣告服務及變數名稱，實際值在 Render 設定。
- 如需新增相依套件，在實作計畫說明用途及必要性。已加入的 `@supabase/supabase-js` 用於瀏覽器端的 Supabase Auth。

## 本次範圍之外

- 成員角色及個別操作權限。
- 將既有本機 SQLite 的資料搬到 Supabase。
- Google 登入、魔法連結和密碼重設。

## 成功標準

1. 有無正式 Supabase 設定，`npm run check` 都能使用獨立的 SQLite 和虛構使用者通過，且檢查過程不連接 Supabase。
2. 未登入時，開啟任一應用程式頁面會顯示登入畫面，CRM API 會拒絕未通過驗證的請求。以已建立的帳號登入後，既有的 CRM 操作均可使用，並能從選單登出。
3. 用一位成員新增公司、聯絡人、商機及活動時，畫面會顯示該成員的 Email。由另一位成員修改時，新增者仍正確，並記錄最後修改者。
4. 從頂欄用部分名稱找得到公司、聯絡人和商機，換用不同英文字母大小寫仍得到相同結果。從搜尋結果可以打開對應的詳情。
5. 使用者選單可切換亮色、深色或跟隨系統。所選模式會保留到下一次開啟，跟隨系統模式會隨裝置設定更新。
6. 本機可以用與 Render 相同的正式啟動方式執行建置後的應用程式，並用已建立的 Supabase 帳號登入、讀取共用資料。
