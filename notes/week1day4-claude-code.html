這一天在做什麼

Day 4 的主題是 Harness Engineering。今天把專案規格、coding standards、自動檢查、hooks 和 CI 接進 Accountable 的日常流程。規格讓 agent 知道產品現況，檢查讓它在出錯時能及早收到回饋。

先在 harness 分支建立這套流程，驗證後合進自己的 main。接著開 dark-mode 分支，把深色模式走完 Day 3 練過的六個階段，並在合併前用審查結果改善 harness。

怎麼讀這份頁面

「要做什麼」提供講義原文、指令和中文說明。「白話說明」解釋每一步的用途。完成後勾選該步的「完成判準」，進度會記在目前的瀏覽器。

「給 Claude 的指示」貼到 Claude Code。「終端機」區塊由你在 repo 根目錄執行。每次 git add . 前可以先用 git status --short 確認哪些檔案會一起提交。

名詞解釋

Harness
圍繞 agent 與專案的工作流程。今天用 repo 文件提供脈絡，用 hooks、測試和 CI 提供回饋，再根據失誤改善規則。
spec、intent、plan
spec 描述整個產品的行為。每次變更的 intent 記下原因、限制與成功標準，plan 記下實作及驗證方式。
Hook
在某個事件發生時自動執行的動作。例如 Git 的 pre-commit 在提交前檢查，Claude Code 的 hook 可在停止或編輯時提供回饋。
CI（Continuous Integration）
把檢查接到共用的執行環境。今天 GitHub Actions 每次收到 push 都會跑，結果與該次 commit 綁在一起。
gitleaks
掃描疑似金鑰與其他秘密的工具。練習會用一組完全虛構的資料，驗證本機和 CI 的兩次攔截。
單元測試覆蓋率
衡量測試執行過多少程式碼。以這個數字掌握測試涵蓋程度，並用具體情境核對行為有被驗證。
循環複雜度
衡量函式有多少獨立控制流程。主線以 ESLint 的 complexity 和 Ruff 的 C901 設定每個函式的門檻。
色彩 tokens
給 UI 色彩角色命名，例如文字、背景與邊框。元件共用同一組名稱，由主題提供對應的色值。
Proof
實作計畫中的驗證章節，列出哪些單元與端對端測試能證明功能完成。
Important
依審查政策判定須在合併前修正的問題。與這次變更相關的問題先修正再驗證。

Add the checks
待完成

要做什麼

給 Claude 的指示
Add npm run check, which runs all of these and fails if any of them fails:
- Prettier and ESLint for the frontend, using the recommended TypeScript, React Hooks and accessibility rules
- ruff format and ruff check for the backend
- A maximum cyclomatic complexity of 15 per function, using ESLint's complexity rule and ruff's C901 rule
- tsc for the frontend and ty for the backend
- gitleaks across the repo, allowing the git-ignored .env
- npm test, with unit test coverage of at least 80%
Add npm run check:quick, which runs the same checks without the end-to-end tests. Add npm run format to fix the formatting. Fix what the checks find, without weakening any rule. If a rule doesn't suit this project, ask me first. Add npm run check to AGENTS.md, run it and show me the output.
  • npm run check 檢查前端 Prettier、ESLint（TypeScript、React Hooks、無障礙）與後端 Ruff。前後端每個函式的循環複雜度上限為 15，型別分別用 tsc 和 ty 檢查。
  • 再用 gitleaks 掃 repo，只允許 Git 已忽略的 .env 例外，最後執行 npm test。講義主線的單元測試覆蓋率門檻為 80%。
  • npm run check:quick 略過端對端測試，其餘檢查照跑。npm run format 會寫入格式修正。請 Claude 把完整指令加到 AGENTS.md，執行並顯示輸出。若規則不適合，先由你決定是否調整。

這通常是今天最久的一步。講義允許在貼出提示詞前調低 80%，或移除 , with unit test coverage of at least 80%。若想在 Claude Code 用平行 agent，可選擇把開頭改為 Use a dynamic workflow to add npm run check，保留後續原文。這通常會用掉更多方案額度。

把檢查接到 Git 與 Claude Code

Add the hooks
待完成

要做什麼

給 Claude 的指示
Add three hooks:
- A lefthook pre-commit hook that formats the staged files, then runs lint, types and gitleaks. Skip the tests, so that it stays quick.
- A hook for this coding agent that runs npm run check:quick when you finish a turn and sends any failure back to you to fix. It should block once and then let you stop, so it can't loop forever.
- A hook for this coding agent that blocks any edit to .env.
Test each one and tell me how you tested it. If this coding agent doesn't support one of these hooks, tell me.
  1. Lefthook 的 pre-commit 先格式化已暫存的檔案，再執行 lint、型別檢查與 gitleaks。略過測試，以縮短每次 commit 的等待。
  2. Claude Code 結束一輪時跑 npm run check:quick，把失敗回傳給 Claude 修正。同一次停止流程最多阻擋一次，避免反覆觸發。
  3. Claude Code 嘗試編輯 .env 時應被攔下。請 agent 分別回報三個 hook 的驗證方法及結果。
終端機 · 提交 hooks
git add .
git commit -m "Harness: hooks"

白話說明

Git hook 在你提交時執行，和使用哪個 agent 無關。另兩個 hook 在 Claude Code 的操作過程給回饋。手動測 .env 的保護可在隔離的工作副本使用空白測試檔，確認操作被攔下。

把完整檢查接到 GitHub Actions

Add CI

要做什麼

到自己的 GitHub fork 開啟 Actions。如果 GitHub 要求啟用 workflows，先啟用。

給 Claude 的指示
Add .github/workflows/ci.yml with one job named check that runs on every push to any branch. It installs gitleaks and runs it across the repo first, so a leaked secret fails the run straight away. Then it installs Node and uv, and runs npm run check with the Google Chrome already on GitHub's runner. If it fails, upload the Playwright report. Add no secrets. astral-sh/setup-uv has no major version tags like v10, so use the full version number of its latest release, and let it install the latest uv.

建立 .github/workflows/ci.yml，只有一個 check job，推任何分支都會跑。先安裝並執行 gitleaks，再準備 Node 和 uv，使用 runner 上的 Google Chrome 跑 npm run check。失敗時上傳 Playwright 報告，不需新增 secrets。

終端機 · 提交並推送 CI 設定
git add .
git commit -m "Harness: CI"
git push fork harness

到 Actions 看 harness 的 run。講義的第一次執行約 15 分鐘。若失敗，把失敗步驟與錯誤貼給 Claude，找出原因、修正並重新 push。

課程指南 · CI 常見問題

  • Set up job 找不到 astral-sh/setup-uv 時，檢查參照是否用了完整的 release tag，例如 v10.3.3 是完整格式，v10 會找不到。講義要求選當時最新的完整 tag，讓 action 自行安裝最新的 uv。
  • 端對端測試使用 GitHub Ubuntu runner 已有的 Google Chrome。若本機成功、CI 失敗，先從 Linux runner 的錯誤與 Playwright 報告找差異。

白話說明

GitHub 上的執行紀錄可以讓你知道推上去的 commit 是否通過。把掃描放在前面，偵測到秘密時就能提早結束。

終端機 · 回到 harness 並刪除本機與 fork 的演練分支

git branch -D make-it-fail
git push fork --delete make-it-fail

課程指南 · 演練後還是失敗

gitleaks 會掃分支歷史。若清理前 npm run check 仍看到假金鑰，確認本機和 fork 上的 make-it-fail 都已刪除。

白話說明

這一步收集兩筆證據。一筆是本機拒絕提交，另一筆是 GitHub 執行秘密掃描後拒絕通過。這兩筆結果分別證明 Git hook 和 CI 的檢查有生效。

# Improve the harness

# Intent: dark mode

## Problem

Accountable only has a light mode, and some people prefer a dark screen.

## Proposed outcome

A dark mode with a toggle on every page, across every section.

## Constraints

- Light mode stays the default, and the app remembers the choice.
- Light mode looks exactly as it does today, apart from the toggle.
- Colors stay in one place, as tokens, with no scattered overrides.
- Text in dark mode meets the same contrast rules as spec.md.
- Charts, dialogs and messages follow the mode too.
- No new dependencies unless the plan makes the case for one.

## Not in this change

- Following the device's own dark mode setting.
- A layout for phones.

## Success criteria

1. npm run check passes.
2. A new end-to-end test proves that the toggle works and is remembered after a reload.
3. Screenshots of the dashboard and the pipeline in both modes are saved in docs/changes/dark-mode/.
  • 每個功能區塊的頁面都可切換。亮色是預設值，重新載入後應保留上次的選擇。亮色外觀維持既有樣式，只新增切換控制。
  • 顏色集中到 tokens。深色文字符合現有 spec 的對比規則，圖表、對話框與訊息一起切換。有理由新增套件時，先在 plan 說明。
  • 這次的範圍以 App 內的主題選擇為準，沿用現有瀏覽器版面。跟隨裝置主題與手機版面留待後續變更。
