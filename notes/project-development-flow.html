# 專案開發 workflow

## 專案設定

- 主分支　〈填寫〉
- 規格入口、區域規格目錄（適用時）、變更紀錄目錄及審查政策所在位置　〈填寫〉
- 本機快速檢查指令　〈填寫〉
- 本機完整檢查指令　〈填寫〉
- 共用 CI 的工作名稱與結果連結　〈啟用時填寫〉
- 正式啟動指令、部署環境與上線驗收方式　〈適用時填寫〉

## 每次變更

- [ ] 開分支。確認工作區與起始提交，從主分支開始。
- [ ] Plan。確認 intent 裡的問題、對象、範圍和成功標準。
- [ ] Design。先讀規格入口，再沿索引查閱受影響的區域與共用規則。更新規格與驗收條件，核對規格差異是否符合已確認的變更意圖。
- [ ] Build。計畫列出順序、風險和 Proof，分段實作並驗證。
- [ ] Test。本機完整檢查已通過，成功標準都有驗收證據。
- [ ] Deploy。獨立核對受影響的規格、實作及測試，修正 Important 問題，再依結果改善既有的 harness。
- [ ] 合併。待合併提交取得完整檢查與適用的 CI 結果，由人核對後合併。
- [ ] Maintain。在交付版本走一次日常操作，記下具體觀察和後續想法。

## 依變更啟用

- [ ] Design 需要拆分規格時，保留原入口作為摘要與索引，按功能搬移細節，核對內容與連結，更新代理閱讀指引和審查政策。先獨立提交規格搬移，再提交產品行為的變更。
- [ ] Test 有介面變更時，用 ui-check 或手動檢查並保存畫面證據。
- [ ] Test 有外部服務時，用授權的驗收環境試跑正式啟動方式，核對適用的 migration 與存取規則。
- [ ] 合併前有共用 CI 時，確認同一個待合併提交的分支 CI 已通過。
- [ ] 合併後需要部署時，確認主分支 CI 已通過，再核對部署版本並從正式網址驗收關鍵操作。

開工前確認環境

  • 環境與共用規則

    裝好 Git、coding agent 和專案工具。在 repo 根目錄確認 agent 能讀到 AGENTS.md 的共用指示，個人偏好留在使用者設定。Day 2 安裝與設定

  • 權限

    允許 agent 執行明確的測試指令。git push 由人確認，限制 agent 讀取 .env。Day 2 權限設定

  • 介面工具與子代理

    有介面工作時，用品牌 skill 統一設計，並用 Playwright MCP 比對畫面及截圖。工具支援子代理時，可預先設定 ui-check 和唯讀的 reviewer。Day 2 品牌 skill · Day 2 瀏覽器工具 · Day 5 子代理設定

開分支做變更

展開 Harness 設定清單

  • 文件與審查規則

    用 AGENTS.md 記錄產品規格、當前變更、撰寫標準與改善流程的入口。審查依 REVIEW.md 核對行為與標準。

  • 本機檢查

    開發中跑快速版，驗收時跑含端對端測試的完整版。Git hook 在提交前處理格式、lint、型別與秘密掃描。

  • CI 與秘密保護

    啟用共用 CI 時，先掃秘密，再跑專案設定的檢查。Day 5 在 CI 跑快速檢查，本機完整檢查涵蓋端對端測試。將金鑰留在 Git 已忽略的 .env 或平台的秘密設定。Day 5 快速 CI

Accountable 用 npm run check:quick 與 npm run check。套用到其他專案時，換成該專案的指令。Day 4 的 Harness 設定步驟

產品規格怎麼組織與維護

每次開工從同一份規格入口了解產品，再依這次變更的範圍查閱細節。以下用 Accountable 的文件路徑示範，套用到其他專案時，將實際位置記入上方的檢核表。

docs/spec.md · 規格入口
每個代理開工先讀。放產品摘要、適用全產品的重要規則，以及能找到各區域規格的索引。
docs/specs/<area>.md · 區域規格
變更碰到該區域時查閱。記錄功能目前應有的行為、適用條件、例外情境及驗收條件。
docs/changes/<branch>/ · 變更紀錄
處理該分支時讀取。intent.md 記錄為什麼改與成功標準，plan.md 記錄實作順序、風險與驗證方式。合併後保留為此次變更的紀錄。
程式與測試 · 實際行為的證據
核對行為時查閱。程式顯示系統實際怎麼運作，測試提供已覆蓋情境的驗證證據。用規格判斷產品應該怎麼運作。

每次變更怎麼讀、怎麼更新

  1. 先讀規格入口，從索引找出直接受影響的區域和共用規則。也確認其他區域是否會使用改動後的資料或行為，再讀當前分支的意圖與計畫（若有）。
  2. 在同一次變更更新受影響的規格與驗收條件。每條共用規則選定一處維護，其他區域以連結引用。例如預期營收的計算規則寫在統計規格，儀表板與看板各自描述呈現時機並連過去。
  3. 審查時對照受影響的規格、實作及測試。若有落差，以已確認的變更意圖判斷。實作偏離既定行為時修正程式，產品方向已確認調整時更新規格。兩種情況都要補足相關的驗收證據。

什麼時候拆分規格

規格容易查找時，可以集中在一份。當同一份文件涵蓋多個功能，找一條規則得反覆翻找時，就按產品區域拆分。

  1. 在原路徑保留摘要、重要規則與索引，將既有細節移到對應區域。核對搬移前後的行為與驗收條件，並確認索引及內部連結都能找到內容。
  2. 更新代理閱讀指引和審查政策。Accountable 會更新 AGENTS.md 與 docs/REVIEW.md，讓代理先讀入口，再查閱並審查受影響的區域規格。
  3. 先獨立提交規格搬移，再提交這次的行為變更。審查者可以逐筆核對文件搬移與行為差異。Day 5 拆分規格 · Day 5 更新產品行為

Accountable 範例 · 調整商機移入議價時的預設成交機率

先從規格入口找到商機與商機看板規則，核對表單變更與跨欄拖放。成交機率也會影響儀表板的預期營收，因此要一起讀儀表板與共用統計規則。

把新機率寫在共用的階段規則，並確認表單與看板規格都指向同一處。驗收時分別用表單及拖放把測試商機移入議價，確認兩種操作都套用新機率，再用已知商機金額核對儀表板更新後的預期營收。

    先寫清楚要解決什麼

    請 agent 訪談你，把答案寫入 intent.md。Day 3 訪談範例

    完成判準 問題、使用者、範圍和可驗證的成功標準已確認。

  3. Design

    審閱變更後的產品行為

    新產品建立 spec.md，依需要選定介面設計稿。既有產品用規格差異審閱變更後的行為，並標出要用原畫面比對的部分。Day 4 規格差異

    先讀規格入口，再沿索引查閱本次影響的區域與共用規則。規格難以查找時，先獨立提交文件重組，再寫這次的行為變更。產品規格怎麼組織與維護

    完成判準 已確認變更後的產品行為與採用的設計，並核對受影響的區域、共用規則及驗收條件。

  4. Build

    先排計畫，再分段實作

    在 plan.md 列出改動、依賴順序與風險，用 Proof 對照每段的驗證。開新 session，依計畫分段做、分段測。如果多人並行，先劃清檔案範圍與相依關係。核對差異與結果後再提交。Day 5 分階段計畫

    完成判準 計畫中的改動和測試已完成，開發中的檢查通過。

  5. Test

    跑完整檢查，親手驗收

    首次 MVP 用 npm test 跑單元和端對端測試。已設定 harness 就跑完整檢查，例如 npm run check。

    親手走過 intent.md 的成功標準。有介面改動時，用 ui-check 或手動操作瀏覽器並留存截圖。首版比對設計稿，既有介面用相同資料與視窗尺寸核對畫面。Day 3 設計稿驗收 · Day 4 主題驗收 · Day 5 UI 檢查

    有外部服務時，自動測試仍用隔離資料。另在授權的驗收環境，以正式啟動方式走關鍵操作，核對這次涉及的 migration 與存取規則。Day 5 Supabase 驗收

    完成判準 完整檢查通過，成功標準都有驗收證據。
