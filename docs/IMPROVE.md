# 改善開發防護機制

在部署（Deploy）階段修正審查發現後、合併前執行這個流程。

1. 回顧這次變更遇到的問題，包含審查發現、開發者做了哪些修正，以及檢查攔下了哪些問題。逐項記錄 Important 問題的重現條件，並與原始實作計畫的 Proof 所列案例比對。
2. 同一錯誤若已發生兩次，能用工具偵測時，就把它納入自動檢查。其餘情況將修正方式寫入 `AGENTS.md` 或 `docs/REVIEW.md`，或請開發者更新 `docs/STANDARDS.md`。若已為審查修正加入回歸測試，確認測試涵蓋第 1 步的重現條件，且標準檢查指令會執行該測試。
3. 移除過時的內容。
4. 更新這份文件，讓下一輪變更能依改進後的流程進行。每次都在最後執行這一步。

## 2026-11-28｜multi-user 回顧

| 發現與重現條件 | 原計畫 Proof 與改善 |
| --- | --- |
| 帳密登入成功，但緊接著的身分驗證回 503，前端清除有效工作階段。 | Proof 提到驗證服務逾時，原測試只涵蓋還原時的 503。加入實際登入入口的回歸測試，先確認修正前失敗，再確認保留工作階段並能重試登入頁面。Vitest 由快速及完整檢查執行。 |
| Supabase 登入或還原時回 429，前端誤判為帳密錯誤或未登入。 | 兩條流程各加入修正前會失敗的回歸測試，並擴充後端 403 與 429 的 API 測試，確認明確未授權與限流分別得到 401 及可重試的 503。 |
| Render 缺少團隊時區與鄰近資料庫的區域。 | 依講義補上 Asia/Taipei 與 singapore。審查政策新增部署時區與區域查核，避免團隊日期與部署機器日期不一致。 |
| 新增 migrations 的 Python 檔案未包含於既有工具範圍。 | 將 Ruff 格式、lint、型別檢查及格式修正指令擴及 migrations，pre-commit 同步涵蓋該目錄。 |

後續變更應依審查政策，分別驗證登入、還原及刷新權杖的錯誤處理，並核對新目錄是否由既有檢查入口涵蓋。
